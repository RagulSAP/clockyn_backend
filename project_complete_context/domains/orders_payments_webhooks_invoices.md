## 4. Business logic

### 4.1 `POST /orders/create` (`gen_orders_functions.py:8-146`)
1. `SELECT user_id FROM users` (:27) -> 404. (org membership, plan existence and `staff_limit` are **not** validated.)
2. `amount <= 0` -> 400 (:31). **The client's `amount` is the price** (docstring :16-19). There is no server price computation; the "credit" the client deducted is never sent or checked.
3. `get_razorpay_client()` (`utils/razorpay.py:42-68`): in-process cache, 5 min TTL (`:67`), loads `gen_razorpay_key WHERE status=1 LIMIT 1`; failure -> 500.
4. One query for payer name/mobile/e-mail, org name, plan name (LEFT JOINs; a bad `plan_id` yields empty `plan_name`, order still created) (:39-58). `order_name = "<plan> - <org>"`.
5. `is_first_payment = count(gen_orders PAID for user) == 0` (:75-80).
6. `receipt = "ord-" + uuid4 hex[:16]`; Razorpay create: `amount=int(amount*100)` paise, `currency='INR'`, `payment_capture=1` (auto-capture), `receipt`, `notes` (11 keys including payer phone/e-mail) (`utils/razorpay.py:14-30`).
7. `INSERT gen_orders (..., status 'CREATED', staff_limit, coupon_code=(upper(trim) or NULL))`, commit (:95-112).
8. Response as in §3. The public **key id** is returned inside the response (top level and `checkout.key_id`); the client has no key of its own and `createOrder` throws if `orderId` or `keyId` is empty (`billing.ts`). The secret is never sent.

### 4.2 `POST /payments/verify` (`gen_payment_functions.py:15-215`)
1. Signature: `HMAC_SHA256(key_secret, order_id|payment_id)` hex compared with `hmac.compare_digest` (`utils/razorpay.py:32-38`) -> 400.
2. Load order joined with plan, user, org **and filtered by `user_id`** (:34-46) -> 404. `status == 'PAID'` -> early success **without activating anything** (:51-52; idempotency by status).
3. `INSERT gen_payments ... ON CONFLICT (razorpay_payment_id) DO NOTHING`; `UPDATE gen_orders SET status='PAID'` (:55-65).
4. Subscription (:67-103): load latest `ACTIVE` `sub_tbl` row (**regardless of `end_date`**), a second identical query for its `plan_id` (:80-85). `same_plan = existing.plan_id == order.plan_id`.
   * `same_plan`: `staff_limit = existing.staff_limit + order.staff_limit`; `end_date = existing.end_date` (**not extended, even if already past**); 
   * different plan or none: `staff_limit = order.staff_limit` (`or 10`); `end_date = utc_today + plan_month months` (`or 12`).
   * Insert a **new** `sub_tbl` row (`uuid4` subscription_id, `start_date = utc_today`, status `ACTIVE`; the `ON CONFLICT (subscription_id)` branch never fires) (:94-103), then `UPDATE sub_tbl SET status='INACTIVE' WHERE org_id=? AND subscription_id != new` (:106-109).
   * `UPDATE free_trial SET is_active=FALSE, end_date=LEAST(end_date, today) WHERE org_id=? AND is_active` (:112-115). `conn.commit()` (:117).
   Mapping to client modes: renew (same plan, 10+ staff) = **adds staff, end date unchanged**; staff-only upgrade (same plan, delta staff) = correct top-up; plan change = replace + fresh term.
5. Invoice (separate, post-commit try/except, :119-199): only when an e-mail is known (`override_email` else `users.email`) (:132,138). `total = order.amount`; `base = round(total/1.18, 2)`; `cgst = sgst = round(base*0.09, 2)` (Python float, half-even); `INSERT gen_invoices` with `invoice_number = 'INV-' || YYYY || '-' || LPAD(nextval('gen_invoice_seq'),4,'0')` (year from DB `NOW()`), `staff_count = new_staff_limit` (the **total** limit, even for a staff-only top-up), `valid_till = end_date`, `payment_date = utc now`; commit. Any exception -> logged, rolled back, **payment stays successful with no invoice**.
6. E-mail (:201-206): `send_invoice_email` starts a daemon thread (`email.py:758-763`) that builds the PDF and sends via AWS SES `send_raw_email` (`email.py:584-755`); failures only logged. Invoice data: place of supply fixed `'Tamil Nadu (33)'`, SAC `998314`, one line item (`<plan> - <legacy product> Subscription`, qty = total staff, rate = base/qty).
7. Response `{success, message, valid_till}`.

### 4.3 Razorpay webhook (`gen_webhook_functions.py:13-76`)
1. `body = json.dumps(payload, separators=(',',':'))` of the **parsed** JSON (not the raw bytes) -> HMAC_SHA256 with `RAZORPAY_WEBHOOK_SECRET` (default `""`) -> `compare_digest` against the header; mismatch -> 400.
2. `INSERT gen_webhook_events(event_id=payload.id, event_type, payload)`; the unique index on `event_id` is the only dedup: a redelivery raises, the handler rolls back and answers **500**, so Razorpay keeps retrying.
3. `payment.captured`: `UPDATE gen_orders SET status='PAID'`; `INSERT gen_payments (user_id, razorpay_payment_id, razorpay_order_id, amount, status) SELECT ... FROM gen_orders ... ON CONFLICT DO NOTHING` (omits `org_id`, NOT NULL in the DDL dump -> would fail unless the live column is nullable, UNVERIFIED). `payment.failed`: `UPDATE gen_orders SET status='FAILED'`. **No subscription, trial or invoice change; other event types only logged to `gen_webhook_events`.**

### 4.4 MSG91 WhatsApp webhook (`:79-143`)
Extracts request id / event / number from several candidate keys, logs the full payload at INFO (phone numbers in logs), inserts into `gen_webhook_events` with `event_id = request_id or "msg91-<event>"` and `event_type = "msg91.whatsapp.<event>"`. Several events (sent/delivered/read) share one request id -> unique violation -> 500 -> events lost.

### 4.5 Invoice PDF and numbering
* Builder `_generate_invoice_pdf` (`email.py:137-553`, ReportLab, A4): header (logo image from `static/`, issuer block hard-coded at `:206-216`, "TAX INVOICE"), meta (No., Date, Terms `Net 0`, Due Date = payment date, Place of Supply default `Tamil Nadu (33)`), Bill To / Ship To (same `format_full_address`, `:64-78`), items table, "Total In Words" (`_num_to_words`, `:110-133`, Indian lakh/crore), summary (Sub Total, optional Discount/IGST, **CGST 9% / SGST 9% labels hard-coded**, Total), authorised signature image `static/` (`:505-509`). Rupee glyph needs DejaVu (`fonts-dejavu-core` installed by the Dockerfile; Helvetica fallback at `email.py:37-61` prints a missing glyph). `discount`, `igst*`, `terms_conditions`, `new_plan`, `previous_plan` are supported by the builder but no caller supplies them.
* The e-mail copy is generated from the live purchase data (`invoice_data` at `gen_payment_functions.py:163-193`); `/invoice/download` and bulk **regenerate from `gen_invoices`** (`email.py:980-1008`, `1141-1166`): they lose `place_of_supply`, phone, valid-till text, and print the **customer's** GSTIN (`company_additional_info.gst_number` / `org_info.org_gst`) in the issuer block via `company_gstin` (`:204-211`).
* Numbering: `INV-<DB-year>-<4-digit zero-padded global sequence>`; the sequence is global (not reset per year), `LPAD` **truncates** values longer than 4 digits (invoice 10000 -> `1000`).
* Bulk (`:1096-1201`): `gi.payment_date::date BETWEEN from AND to` (UTC dates), loops all rows generating a PDF each in the request thread, names `<invoice_number>.pdf` (dup -> `<number>_<payment_id>.pdf`), skips failed PDFs, appends an Excel summary built by `_build_invoice_summary_workbook` (`:1030-1093`; columns: Invoice Number, Payment Date, Organization, GST Number, Customer Name, Customer Email, Customer Mobile, Plan Name, Staff Count, Coupon Code, Base Amount, CGST, SGST, Total Amount, Payment ID, Order ID, Valid Till + a TOTAL row), whole ZIP in memory.

### 4.6 Time zone / IDs
Payment dates use UTC (`get_utc_now().date()`); the invoice displays UTC dates; DB year for the number uses DB timezone. Ids: invoice uuid via `gen_random_uuid()`, subscription uuid4, receipt `ord-<16 hex>`.

## 8b. Changes (WP10, decisions D-12 / D-13 / D-20; migration 031)

* **Server prices everything.** `core_functions/pricing.py` (pure, `Decimal`, whole-rupee half-up discount and GST exactly like the app's `pricing.ts`) is called by `POST /orders/quote` and `POST /orders/create`. Create ignores the client `amount` (kept optional in the body; a different value is logged as a warning and stored in `gen_orders.client_amount`); the Razorpay order and `gen_orders.amount` carry the server total. The response keeps every key the app reads and adds `quote`. Plan price = `gen_plans.plan_amount` (per staff per month); coupon = `gen_coupons` (new optional rule columns); current plan = latest ACTIVE/EXPIRED `subscription` row. The five reference totals (8,496 / 7,646 / 8,602 / 3,540 / 1,510) are asserted in `tests/test_pricing.py` and `tests/test_orders_billing.py`.
* **`mode`** (`new|renew|upgrade`) is an optional request field (new app builds should send it). Without it the server prices every legitimate candidate and picks the one equal to the amount the app displayed (see `pricing.pick_mode`); the amount only selects, it is never charged. Order guards: user exists, org exists and belongs to the admin (`BILLING_ENFORCE_ORG_OWNER`, default on), plan exists, staff 1..10000 and the per-mode minimum, total > 0, an unusable coupon refuses the order (400).
* **Renew semantics (P1-13).** `activation_terms()`: renew extends from the current end date while it has not passed (IST, inclusive), else from today, and sets the staff limit to the ordered staff (never `existing + ordered`); upgrade adds the extra staff and keeps the end date; new replaces staff and runs `today + plan_month`. Dates are IST. `expire_due_subscriptions(today_ist, org_id=None, cursor=None)` writes `EXPIRED` and runs at the start of `GET /plans/subscription/{org}` and `GET /plans/plan-status/{org}` (and so on every plan gate).
* **Activation is one function used by both callers** (`gen_payment_functions.activate_paid_order`): the order row is locked (`FOR UPDATE`), an activated order is a no-op, the subscription id is derived from the order id (`sub-<razorpay_order_id>`, unique index = second guard), previous subscriptions go INACTIVE, the trial is closed, `gen_orders.status = PAID` + `activated_at`, payment row (with `org_id`) and invoice are written in the same transaction. Verify-then-webhook and webhook-then-verify both activate once; a replayed verify answers `{success, message:'Payment already verified', valid_till, plan_id}`. A legacy order marked PAID by the old webhook without a subscription is repaired by the next verify.
* **Webhook:** signature = HMAC-SHA256 of the raw request bytes with `RAZORPAY_WEBHOOK_SECRET`, constant-time compare; missing header or wrong signature 400; secret unset 503. Events are de-duplicated on the `X-Razorpay-Event-Id` header (`ON CONFLICT (event_id) DO NOTHING`, duplicate answers 200 `{success:true,duplicate:true}`). `payment.captured` and `order.paid` activate; the paid amount (paise) and currency must equal the stored order amount, otherwise `gen_orders.payment_flag = 'AMOUNT_MISMATCH'`, nothing is activated and later verify calls answer 409; `payment.failed` never overwrites a paid order; unknown orders / other events are stored and answer 200. A processing error answers 500 so Razorpay retries (the event row is rolled back with it).
* **Invoice:** written inside activation under a savepoint (a failure never undoes the payment, it is logged), one per payment (unique index on `razorpay_payment_id`, `invoice_number`), number `INV-<IST year>-<seq, at least 4 digits, never truncated>`, base/GST from the stored order breakdown (no more `total/1.18`), CGST+SGST when the customer's state equals the seller place of supply (`SELLER_PLACE_OF_SUPPLY`) or either is unknown, else IGST (`gen_invoices.igst`; the e-mail builder already prints `igst`). The invoice is created even when no e-mail is known.
* **Invoice number collisions (independent review fix).** A unique violation (SQLSTATE 23505) of `invoice_number` rolls back to the savepoint and retries up to 3 times with a fresh `nextval` (sequences are not rolled back, so each retry gets a new number); if every attempt fails an ERROR is logged with the Razorpay order id and payment id and the activation still commits (the invoice and its e-mail are then missing but never silently). Any other insert failure is logged as an ERROR with the order id, not retried. Migration 031 and the DDL (section 5, after `CREATE SEQUENCE`) run an idempotent `DO` block: when `gen_invoices` has rows, `setval('gen_invoice_seq', GREATEST(max trailing number of invoice_number, 1))`; a no-op on an empty table. `scripts/check_schema_consistency.py` needed no change (it ignores DO blocks without ALTER/CREATE fragments). Tests: `tests/test_review_fixes_crm_invoice.py`. Unverified without a database: the `setval` block and a real 23505 from `uq_gen_invoices_invoice_number` (the code detects it by `pgcode`).
* **Not done here:** `/invoice/download` and bulk regenerate from `gen_invoices` in `utils/email.py` (not in this WP's files) still print only cgst/sgst, so an IGST invoice downloaded later shows 0 tax lines; flat coupons are priced by the server but the app's coupon box only knows percentages.
